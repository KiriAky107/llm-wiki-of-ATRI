# 电费插件的输入边界：同一个"静默降级"，三个变种

- **建档**：2026-09-29（晚间收尾）
- **状态**：🟢 三类**均已修 + 真实数据实测 + 回归通过**；**待主人实机复验一次**
- **触发场景**：主人当天三次追问同一件事——**"错误的输入会发生什么"**

---

## 一、一句话总结

**同一个毛病长出了三张脸：输入无法被正确理解时，程序不报错，而是"猜一个"然后照常输出。**

于是**用户的输入与看到的输出之间，没有因果关系**——主人当天的原话是"随机返回"。

| 变种 | 谁发现 | 表现 | 根因 |
|:---|:---|:---|:---|
| ① **垃圾输入** | 主人随手敲三行 | 无法识别的输入被降级成"只给了校区"，照样返回 26 个楼栋 | 解析器**只有两种出口**（查到 / 没找到），**没有"看不懂"这个状态** |
| ② **消息尾缀** | 主人实机复测 | 修好 ① 之后，**合法输入也全挂** | 同机另一插件给每条消息尾部追加了编号；本机拿到的是**被改装过的副本**，却拿它去做字符校验 |
| ③ **数字匹配** | 主人 22:01（"依旧 0 等于 10"） | **`0` → 10 号楼**；`06` / `09` → 永远找不到楼栋 | 选项匹配用的是**子串包含**（`"0号公寓" in "10号公寓"` 成立），而不是数字相等 |

---

## 二、变种 ③ 的根因细节（最隐蔽的一个）

原实现：

```python
def _pick(items, key, needle):
    for it in items:
        if needle in str(it.get("label", "")):   # ← 子串匹配
            return it
```

调用处传的是 `f"{build_no}号公寓"`，于是：

- `build_no = "0"` → needle `"0号公寓"` → 遍历到 `10号公寓` 时**子串命中** → 悄悄查了 **10 号楼**；
- `build_no = "06"` → needle `"06号公寓"` → **谁都不是它的子串** → 返回 None → "永远找不到"。

**同一句输入，一边是悄悄地错，一边是永远找不到——两个毛病同一个根。**

---

## 三、修法

1. **新增按数字精确匹配** `_pick_no()`：取选项名开头的数字做**整数比较**（`6号公寓` → 6、`101房` → 101），楼栋与房间都改走它；
2. **`_pick()` 调整为三段式**：**先精确 → 再数字 → 最后才子串**（校区名仍需模糊匹配，故保留最后一层）；
3. 顺带白拿一个好处：**前导零自动归一**（`06` → 6 号楼、`09` → 9 号楼）。

**没有做的事情（刻意的）**：没有把 `_pick` 的子串匹配整个删掉——校区名（"含浦" → "含浦学生宿舍"）依赖它。**收窄的是"数字类"匹配，不是全部。**

## 五、要记住的三条

1. **只测 happy path ＝ 没测。** 我修好 ① 之后宣布"27 例全过"——那 27 例**全是合法输入**。主人随手敲三行垃圾，当场撞出两个。
2. **同一个坑在同一个位置栽了两次**：① 的"残留校区词"补过一次，重写解析器时又漏了；③ 的"子串匹配"也属于**同一个"用包含代替相等"的思路**。→ **它需要的不是再修一遍，而是把用例固化成文件、每次改完就跑。**（主人中午提过的那份 27 例用例，**尚未落成 `test_parse.py`**，仍挂账。）
3. **入参不一定是用户打的原文。** 修 ① 之后全挂，因为消息在到达我之前**被别的插件改装过**。→ **以后凡是"我读到的内容"要参与判断，先确认它是不是原文。**
